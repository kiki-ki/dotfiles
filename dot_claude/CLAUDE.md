# CLAUDE.md

## 基本姿勢

- 不確実なことは推測で埋めず、確認するか「分からない」と明示する
- 作業を終えて完了と言う前に、principle-prove-it-works スキルを呼んでから確かめ、その結果を示す
- 大きな変更や破壊的な変更の前に、計画を示して同意を得る
- 設計やアプローチに疑問があれば率直に指摘する。過剰な謝罪・前置き・追従はしない

## 言語

- 会話は settings の `language` に従う
- 会話以外に書き出すもの（コミット、PR、issue、コードのコメント、ドキュメント）は、書き込む先（リポジトリの履歴、同じファイル、周辺のコード、既存のスレッド）で使われている言語に合わせる。手がかりがなければ会話の言語にし、言語を確認するためだけに質問しない

## コーディング

- ブランチ名には `kiki-ki/` を付ける（例: `kiki-ki/add-hoge-page`）
- コメントは既定で書かない。後からコードを読む人が、コードと git の履歴だけでは分からない情報（なぜこうしたか、守るべき条件、回避策の理由など）だけを、1 行で書く

### コミット

- Conventional Commits に従い、`type(scope): summary` の 1 行で書く
- secret や credential は絶対にコミットしない
- 1 コミットには 1 つの論理的な変更だけを入れる
  - 関係のない変更を混ぜない
  - 各コミットの時点でビルドとテストが通る状態を保つ
  - ただし細かく分けすぎない（typo 修正の連続、論理的に切り離せない変更の分割など）

## PR と issue

- PR や issue を書く前に、その作業専用のスキル（plugin やプロジェクトのスキルを含む）がないかを確かめ、あれば先に呼んで従う
- PR は `gh pr create --draft` で draft として作り、作ったら PR の URL をユーザーに伝える
- PR のタイトルは `type(scope): summary` の形で簡潔に書く
- PR の本文には、diff から読み取れないことだけを、レビュアーが変更を理解して確かめるのに必要な量だけ書く
  - 書かないもの: ファイルや関数ごとの変更の列挙、コードの逐語的な説明、根拠のない「影響なし」、絵文字や太字などの装飾、セッション中のユーザーとの細かいやり取り
- `gh` で issue や PR に書き込むとき（作成、コメント、編集）は、ユーザーや team をメンションしない（`@username`、`@org/team` を含めない）。ハンドル名を書く必要があれば、バッククォートで囲むか言い換える
- `--body "$(cat <<'EOF' ... EOF)"` の本文では、backtick・`$`・`\` をエスケープしない。シングルクォートの heredoc は本文をそのまま扱うため
- 本文で他の issue や PR を参照するときは、`#123` ではなく完全な URL（`https://github.com/owner/repo/issues/123` など）で書く
