# CLAUDE.md

以下のルールに従って作業すること。

## 基本姿勢

- 不確実なことは推測で埋めず、確認するか「分からない」と明示する
- 作業を終えて完了と言う前に、principle-prove-it-works スキルを呼んでから確かめ、その結果を示す
- 大きな変更や破壊的な変更の前に、計画を提示して同意を得る
- ファイルを編集・新規作成する前に、関連する周辺コードや既存の構造・命名規則を確認する
- 設計やアプローチに疑問があれば率直に指摘する。過剰な謝罪・前置き・追従はしない

## 言語

- 会話は settings の `language` に従う
- 会話以外に書き出すもの（コミット・PR・issue・コードのコメント・ドキュメント）の言語は固定せず、書き込む先（リポジトリの履歴、同じファイル、周辺のコード、既存のスレッド）で使われている言語に合わせる
  - 手がかりがなければ会話の言語にする。言語を確認するためだけに質問しない

## コーディング

- 作業時に作成するブランチ名は `kiki-ki/` prefix とすること（例: `kiki-ki/add-hoge-page`）
- コードをなぞるだけのコメントを書かない。コメントは「なぜ」を説明するためだけに書き、必要十分な量にする

### コミット

- Conventional Commits に従う: `type(scope): summary`
- コミットメッセージは簡潔に1行で記載する
- secret や credential を絶対にコミットしない
- 1コミット = 1つの論理的な変更を原則とする
  - 関係のない変更を同じコミットに混ぜない
  - 各コミット時点でビルド・テストが通る状態を保つ
  - ただし過度に小さく分割しない（typo 修正の連続、論理的に不可分な変更の分割など）

## プルリクエスト / イシュー

- PR は `gh pr create --draft` で必ず draft として作成し、作成後に PR URL をユーザーに伝えること
- PR タイトルは Conventional Commits の形式に従う: `type(scope): summary`（簡潔に）
- PR 本文は diff が語れないことだけを書く。レビュアーが変更を理解・検証するのに必要十分な量に絞り、レビュアーが理解しやすい形式で記載する
  - 書かないこと: ファイル・関数単位の変更列挙、コードの逐語的な説明、根拠のない「影響なし」宣言、絵文字や太字などの装飾、セッションで行なったユーザーとの細かいやり取り
- issue を起票するときは `/work-create-github-issue` スキルに従うこと
- `gh` で issue や PR に書き込むとき（作成・コメント・編集）、ユーザーや team へのメンションをしない（`@username`、`@org/team` を含めない）
  - 本文中にハンドル名を書く必要がある場合はバッククォートで囲むか言い換える
- `gh` で issue や PR に書き込むとき、`--body "$(cat <<'EOF' ... EOF)"` の本文では backtick / `$` / `\` をエスケープしない（シングルクォート heredoc は本文を完全リテラル扱いするため）
- issue や PR の本文で他の issue や PR を参照するときは、`#123` のような短縮形ではなく完全な URL（`https://github.com/owner/repo/issues/123` 等）で記載すること
