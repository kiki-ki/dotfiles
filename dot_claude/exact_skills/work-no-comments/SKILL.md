# work-no-comments

コメントの判定をサブエージェントに任せ、その結果を検査してから対処する。

「このコメントの情報はコードから読めるか」は、書いた本人には判断できない。文脈を知っているので、どのコメントも必要に見えるからだ。

## 範囲

渡されたファイルか diff を対象にする。なければ、ベースブランチ（既定は `main`）に対する今の diff（作業ツリーを含む）を対象にする。

## 手順

1. **判定を任せる。** Agent ツールで general-purpose を 1 体起動し、[references/checker-prompt.md](references/checker-prompt.md) の全文と範囲を渡す。規則は言い換えずにそのまま渡す。判定役はコメントだけを削除し、`RESHAPE` と `SUPPRESSION` のフラグを返す。
2. **結果を検査する。** 判定役の報告と diff を、checker-prompt.md と同じ規則で確かめ、次のものを却下する。
   - コメント以外への編集
   - 範囲外への編集
   - checker-prompt.md の「残すコメント」に当たるものの削除
   - 理由が事実と違うフラグ
   - 意図して残しているコードを悪者扱いするフラグ

   却下した削除は元に戻す。判断がつかない削除は、戻さずにそのままにする。範囲内の lint や型チェックの抑制を判定役が見落としていないかも確かめる。報告全体を却下したときは、問題点を示して 1 回だけやり直させる。2 回目も却下なら、未解決として報告して終える。
3. **小さな修正をする。** 受け入れた `RESHAPE` のうち、名前の変更、定数への切り出し、型の追加、使われない経路の削除、正しい API への置き換えで済むものは、その場で直す。コードで表せるようになったコメントは消す。構造を変える必要がある修正は、案を示してユーザーの判断を待つ。
4. **回避策は根本から直す。** 受け入れた回避策のフラグは、[principle-fix-root-causes](../principle-fix-root-causes/SKILL.md) に従い、範囲内で根本から直す。根本原因が範囲外なら、範囲内でできる最小の修正にとどめ、残りを未解決として報告する。症状を黙らせるガードは足さない。
5. **制約を仕組みにできないか提案する。** 「消すな」「文言を変えるな」「変える前に X に相談」のような制約のコメントは、自分たちが変えられないものについてなら残す。自分たちのコードについてなら、[principle-encode-lessons-in-structure](../principle-encode-lessons-in-structure/SKILL.md) に従い、範囲内でいちばん安く守らせる方法（型、実行時チェック、テスト、lint）を提案して承認を待つ。承認されたら仕組みを入れてからコメントを消す。承認されなければコメントを残し、制約が仕組みで守られていないことを報告する。
6. **報告する。** 削除数、戻したコメント、やり直しの回数、示した案、行った修正、仕組みの提案と入れたもの、仕組みで守られていない制約、その他の未解決事項を報告する。
