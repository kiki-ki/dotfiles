# creating-github-issue

issue の役割は、起票者の頭の中にしかない文脈を着手する人へ引き渡すこと。
本文だけを読んで「着手でき、close の判断ができる」状態を目指す。

## 手順

1. 起票したい内容をユーザーから受け取り、必要なら関連コード / PR を調査して整理する
2. パラメーターを確認する（会話から自明な場合は確認済みとして提示するだけでよい）
   - リポジトリ: 未指定ならカレントディレクトリのリポジトリを候補として確認する
   - ラベル: 付与するものがあるか確認する。付与する場合は `gh api` で存在を確認してから付ける
3. テンプレートに沿って本文ドラフトを作成する
4. ドラフトをユーザーに提示し、合意を取る。起票は外部投稿なので、合意なしに実行しない
5. `gh issue create --repo <owner>/<repo> --title "..." --body "..."` で起票する（ラベルを付与する場合のみ `--label <label>` を追加）
6. 返却された issue URL をユーザーに伝える

## ルール

- タイトルは `scope: summary`（scope は対象のサービス・コンポーネント名）

## 本文テンプレート

デフォルトは次のセクション構成。issue の種類に応じて適宜調整する。

```markdown
## 概要

作業者が内容を掴みやすい1〜3行の要約（作業リストではない）。

## 背景・目的

なぜ必要か。着手者が判断に迷ったとき立ち返れるように書く（経緯の網羅ではない）。
経緯が分かるリンクがあれば紐づける。

## ゴール

- 何が満たされたら close できるかを、検証可能な箇条書きで（作業リストや「改善する」等の願望ではない）
- 調査系なら「何が分かれば/決まれば完了か」とアウトプット先（issue コメント、ドキュメント等）

## 作業内容

- [ ] ゴールまでの作業を分かっている範囲で列挙（ゴールの言い換えではない）
- [ ] 着手後に更新してよい。起票時点で未定ならセクションごと省略する

## 参考情報

- （関連ファイル・類似 PR・ドキュメント。脈絡のないリンクの羅列にしない）
```

補足:

- スコープが膨らみそうな場合は「やらないこと」をゴールに追記する
- ゴールが複数の独立した話になっていたら、issue を分割するサイン
