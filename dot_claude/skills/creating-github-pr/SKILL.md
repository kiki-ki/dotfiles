# creating-github-pr

diff は「何をどう変えたか」をすでに語っている。本文の役割は、diff が語れないことをレビュアーに伝えることに絞る。

## 手順

1. ブランチの差分（コミット一覧・diff）を確認し、変更の全体像を把握する
2. 本文を作成する
3. `gh pr create --draft --title "..." --body "..."` で draft PR を作成する
4. 返ってきた PR URL をユーザーに伝える

## ルール

- PR は必ず draft で作成する
- タイトルは Conventional Commits の形式に従う: `type(scope): summary`（簡潔に）

## 本文テンプレート

デフォルトは次の3セクション構成。

```markdown
## 背景

なぜこの変更が必要か（実装の説明ではない）。
対応する issue があれば完全 URL でリンクする（close する場合は `Closes <URL>`）。

## 変更内容

振る舞いがどう変わるか、変更により起こりうるリスクを記載する (diff の要約を書かない)。

## 検証

レビュアーが再現できる確認手順。コマンド・操作・期待する結果を記載する。
```

## 書かないこと

- ファイル単位・関数単位の変更列挙（diff を見れば分かる）
- コードの逐語的な説明、追加した関数やフラグの一覧
- 根拠のない「リスクはない」「影響なし」の宣言（根拠があるなら根拠の方を書く）
- 同義の内容の繰り返し、絵文字や太文字などの装飾
