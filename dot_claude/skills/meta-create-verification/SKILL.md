# meta-create-verification

アプリを起動し、ユーザーと同じように操作し、証拠を残すための手順を、プロジェクト専用のスキル `.claude/skills/verify-<app>/` として生成する。言語やフレームワークは問わない。生成したスキルを読むのは、アプリを見たことがないまま作業の途中で開く次のエージェントだ。

頼まれていないのに発火したときは、始める前に作るかどうかをユーザーに聞く。

## 1. リポジトリから調べる

次のことはコードベースから調べ、分からないことだけをユーザーに聞く。

- **触る場所**: ユーザーが実際に使うもの（Web UI、CLI・TUI、デスクトップアプリ、API、モバイルアプリ、ライブラリ）。複数あれば主なものを選び、残りを書き留める。
- **起動**: ローカルでの起動方法。リポジトリが文書にしている開発用コマンド（パッケージのスクリプト、Makefile、README）を優先する。ポート、環境変数、初期データ、認証も書き留める。
- **操作**: エージェントがプログラムから操作する方法。下の「操作手段の選び方」に従う。
- **観察**: 取れる証拠（スクリーンショット、端末の記録、レスポンス、ログ、終了コード、DB の状態）。
- **隔離**: 2 つのインスタンスを同時に動かせるか（ポート、データディレクトリ、プロファイル）。できなければ、生成するスキルにそう書く。共有のインスタンスを二重に操作してユーザーの作業を壊すくらいなら、操作を断る。

そのままではビルドも起動もできないなら、生成の前に直すか、何が壊れているかを正確に報告する。壊れた状態に合わせて書いた手順は間違っている。検証に関係のないファイルの欠落（使われない静的ディレクトリ、サンプル設定など）が起動を妨げているだけなら、生成するスキルがそれを作ってよい。その場合は検証用であると書き、片付けで消す。

### 操作手段の選び方

このスキルは操作用の道具を同梱しない。プロジェクトに合わせて選ぶ。

1. リポジトリにすでにある仕組みを使う。Playwright や Cypress のテスト、expect スクリプト、PTY のヘルパー、curl で叩けるエンドポイント、デバッグ用ポートなど。
2. なければ、この環境で使える汎用の手段から選ぶ。Web や Electron ならブラウザ操作（Playwright、CDP、ブラウザ操作の MCP やスキル）、CLI・TUI なら tmux か PTY、サービスなら HTTP。
3. どれが使えるか判断できないとき、新しい依存を入れる必要があるときは、選択肢を挙げてユーザーに聞く。依存を勝手に足さない。

## 2. スキルを生成する

`.claude/skills/verify-<app>/SKILL.md` を書く。frontmatter には `name: verify-<app>` と、アプリ・触る場所・使う場面を含む `description` を入れる（frontmatter がないとスキルとして登録されない）。次の節を、調べて分かった事実だけで書く。プレースホルダーは残さない。

- **Launch**: 検証用にアプリを起動する正確なコマンド、起動が済んだことの見分け方（ログの行、ポートの応答、プロンプト）、停止方法。すぐ終わる CLI や TUI には起動し続けるサーバーがないので、ビルドか依存のインストールを一度だけ行い、操作のたびに隔離した PTY か tmux のセッションを開く、と書く。
- **Doctor**: 「このインスタンスを操作してよいか」を確かめる読み取り専用のチェック。プロセスが動いている、バージョンやビルドが正しい、ポートを使っているのが自分のインスタンスである、認証が有効である、を確かめる。何かおかしいときは最初にこれを実行する、と書く。
- **Drive**: このリポジトリの実際のセレクタやコマンドを使った操作手順。例ではなく実物を書く。座標やタブ順ではなく、変わりにくい目印（ARIA ラベル、data 属性、プロンプトの文字列、ルートのパス）を使う。
- **Evidence**: 何を証拠として取り、どこに置くか。証拠の基準も書く。
  - 内部のセッターやテスト専用のエンドポイントではなく、ユーザーが通る経路で操作する。
  - 最後の画面だけでなく、操作とその結果の状態を両方取る。
  - 見えるものに加えて、副作用（書かれたファイル、追加された行、送られたメッセージ）を確かめる。
  - モックを使うのは、本番でも外部システムと切り離されている箇所だけにする。
  - dry-run やテストモードを使うときは、名前を信じずに、実際に何が省かれるか（ファイル、ネットワーク、git の ref）を観察して確かめる。dry-run でもネットワークに触れたりブラウザを開いたりするものがある。
- **Cleanup**: 検証で起動したものの止め方。プロセス名で kill せず、自分が起動したプロセスだけを止める。消すのはインスタンスと一時的な状態で、証拠は消さない。証拠はスキルに書いた場所に残す。
- **Helpers**: スキルに同梱するスクリプトは実行できる状態にし、呼び出し方を本文に書く。
- **Maintenance**: 「手順や地図が今のアプリと合わなかったら、meta-maintain-verification スキルで地図を直す。直すのは地図だけで、プロダクトのコードには触れない。地図が古いのか、アプリが退行したのかを区別する」とそのまま書く。

## 3. 機能の地図を作る

`.claude/skills/verify-<app>/features/README.md` と、ユーザー向けの機能ごとに 1 ファイルを作る。最初は、ルート、コマンド、メニュー、ドキュメントから主な 3〜5 個を選ぶ。形は [references/feature-map-example/](references/feature-map-example/) に合わせる。

各ファイルには、ユーザーの視点で、その機能が何か、どうたどり着くか、どう操作するか、動いていることを示す最終状態は何かを書く。H2 は `Sub-features`、`How to get to it (user POV)`、`Driving it with <harness>`、`Gotchas` の 4 つにする。

地図は、このリポジトリで保守する検証の情報源だ。地図に入口が複数あるのに 1 つしか通していない確認は、確認として不十分だ。

## 4. 渡す前に、生成したスキルを実行する

生成したスキルの手順を、最初から最後まで一度実行する。起動、doctor、地図にある機能 1 つの操作、証拠の取得、片付けの順だ。機能は 1 つで足りる。残りは次回以降のために地図にある。

片付けの後で、書いた場所に証拠が残っていることを確かめる。証拠まで消える片付けは不合格だ。失敗した箇所を直し、失敗するたびに片付けも実行して、プロセスやポートを残さない。一度も実行していない検証スキルは、完成品ではなく下書きだ。

## 5. 保守の方法を伝える

アプリが変わったら meta-maintain-verification で地図を直せることを伝える。点検の頻度は、聞かれたときだけ提案する。
