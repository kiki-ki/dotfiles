# meta-create-verification

まともなプロジェクトには、本物のアプリを動かして振る舞いを証明する、スクリプト化された手段が要る。アプリを起動し、ユーザーと同じように機能を操作し、証拠を残す。このスキルは、それをリポジトリに合わせたプロジェクト専用スキル `.claude/skills/verify-<app>/` として生成する。生成物の読み手は人間ではなく次のエージェントだ。そのエージェントはアプリを見たことがなく、作業の途中で予備知識なしにこれを読む。

## 1. ユーザーではなくリポジトリに聞く

次の問いにはコードベースから答え、観察できないことだけをユーザーに聞く:

- **表面:** ユーザーが実際に触るものは何か。Web UI、CLI/TUI、デスクトップアプリ、API、モバイルアプリ、ライブラリ。複数あるなら主要なものを選び、残りは書き留める。
- **起動:** ローカルでどう起動するか。リポジトリ自身が文書化した開発用コマンド（パッケージのスクリプト、Makefile、README のクイックスタート）を優先する。ポート、環境変数、シードデータ、認証を書き留める。
- **操作:** エージェントはどうやってプログラムから操作できるか。下の「操作手段の選び方」に従う。
- **観察:** どんな証拠を取れるか。スクリーンショット、端末の記録、レスポンスボディ、ログ、終了コード、DB の状態。
- **隔離:** 2 つのインスタンスを並べて動かせるか（ポート、データディレクトリ、プロファイル）。できないなら生成するスキルにそう書く。共有インスタンスを二重に操作してユーザーのセッションを壊すより、断るほうがよい。

チェックアウトがそのままではビルドも起動もできないなら、生成の前にそれを直す（か、正確に報告する）。壊れた土台に対して書かれたスキルは、間違った手順を教える。関係のない欠けたアセット（API が配信しない静的ディレクトリ、サンプル設定など）が起動を妨げているなら、生成するスキルがそれを作ってよい。ただし検証用の足場であると明記し、クリーンアップで消す。

### 操作手段の選び方

このスキルは UI を操作する道具を同梱しない。プロジェクトの状況を見て選ぶ:

1. リポジトリにすでにある仕組み: Playwright/Cypress のテスト、expect スクリプト、PTY のヘルパー、curl で叩けるエンドポイント、デバッグ用ポート。
2. なければ、この環境で使える汎用の手段から表面に合うものを選ぶ。Web や Electron ならブラウザ操作（Playwright、CDP、ブラウザ操作の MCP やスキル）、CLI/TUI なら tmux か PTY、サービスなら素の HTTP。
3. どれが使えるか判断できない、または新しい依存を入れる必要があるなら、選択肢を挙げて人間に聞く。勝手に依存を足さない。

## 2. スキルを生成する

`.claude/skills/verify-<app>/SKILL.md` を書く。YAML frontmatter に `name: verify-<app>` と、アプリ・表面・使う場面を含む `description` を入れる（frontmatter がないとスキルとして登録されない）。以下の節を、聞き取りで実際に分かったことに基づいて書く（プレースホルダーを残さない）:

- **Launch:** 検証用にアプリを起動する正確なコマンドと、準備完了の見分け方（ログの行、ポートの応答、プロンプト）。停止方法も書く。短命な CLI や TUI では生かしておくサーバーがない。その場合の起動とは、バイナリのビルド（か依存のインストール）を一度だけ行い、操作のたびに隔離した PTY か tmux のセッションを始めることだ。
- **Doctor:** 「このインスタンスは操作する価値があるか」に答える、読み取り専用のチェックをひとつ。プロセスが生きている、正しいバージョン／ビルド、ポートがこちらのもの、認証が有効。何かおかしいと思ったら、エージェントはまずこれを実行する。
- **Drive:** このリポジトリの本物のセレクタやコマンドを使った操作手順。例ではなく実物を書く。座標やタブ順より、安定したハンドル（ARIA ラベル、data 属性、プロンプト文字列、ルートのパス）を優先する。
- **Evidence:** 証明のために何を取り、どこに置くか。証明の基準を書く:
  - 内部のセッターやテスト専用のエンドポイントではなく、本物のユーザーの経路を通す
  - 最終画面だけでなく、操作とその結果の状態を取る
  - 見えるものと一緒に副作用（書かれたファイル、挿入された行、送られたメッセージ）を確かめる
  - モックは、本番の境界がすでに外部システムを隔離している箇所に限る
  - 安全な経路が dry-run やテストモードなら、名前を信じず、実際に何を飛ばすかを観察して確かめる（ファイル、ネットワーク、git の ref）。dry-run でもネットワークに触れたりブラウザを開いたりするものがある
- **Cleanup:** 実行で作ったインスタンスの片付け方。プロセス名で kill しない。自分が起動したものを kill する。クリーンアップで消すのはインスタンスと一時的な状態で、証拠は消さない。証拠はスキルが名指しした場所に残る。
- **Helpers:** スキルが同梱するスクリプトは実行可能にし、呼び出し方をスキル本文に書く。読み手が解読しなければならないヘルパーはヘルパーではない。

## 3. 機能の地図を作る

`.claude/skills/verify-<app>/features/README.md` と、見つけられたユーザー向けの機能ごとに 1 ファイルを作る（最初はルート、コマンド、メニュー、ドキュメントから上位 3〜5 個）。形は [references/feature-map-example/](references/feature-map-example/) に従う（README の索引と、機能ごとのファイル）。各ファイルはユーザーの視点で、その機能が何か、どう辿り着くか、どう操作するか、動いていることを証明する観察可能な最終状態は何かに答える。H2 は `Sub-features`、`How to get to it (user POV)`、`Driving it with <harness>`、`Gotchas` の 4 つ。地図はリポジトリで保守する検証の情報源だ。地図が複数の入口を挙げているのに、都合のいい 1 つだけを通した証明は不完全だ。

## 4. 渡す前に、生成したスキルを証明する

生成したスキル自身の指示を最初から最後まで一度実行する: 起動、doctor、地図にある機能を 1 つ操作（1 つで足りる。残りは後の実行のために地図がある）、証拠の取得、クリーンアップ。クリーンアップの後、名指しした場所に証拠がまだあることを確かめる。証拠を食うクリーンアップはこのステップで不合格だ。失敗したところを直す。失敗した反復のたびに生成したクリーンアップも実行し、壊れた試行がプロセスやポートを置き去りにしないようにする。一度も実行されていない生成スキルは下書きであって、成果物ではない。

## 5. 保守のループを案内する

アプリの変化に合わせて地図を正直に保つために、`/meta-maintain-verification` を案内する。頻度はユーザーに聞かれたときだけ提案する。
