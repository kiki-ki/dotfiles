# Notes の検証の地図

このディレクトリは、Notes のユーザー向けの振る舞いを検証するための、保守されている情報源だ。アプリを操作する前に索引を読み、該当する機能のファイルを手順として使う。

（これは架空のアプリ Notes と、架空の操作ツール `control-notes` を使った例。実際に生成するときは、そのプロジェクトで選んだ操作手段に置き換える。）

## 前提条件の基準

- 使い捨てのデータディレクトリで Notes を `http://127.0.0.1:4173` に起動する。
- 並行実行が状態を共有しないよう `NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID` を設定する。
- `Quarterly plan` と `Grocery list` というタイトルのノートを投入する。
- `control-notes` と `notes` CLI を `PATH` に置く。
- `control-notes doctor` を実行し、期待する URL、データディレクトリ、ビルドのリビジョンを要求する。
- この検証実行が起動したのではないインスタンスは決して操作しない。

## 操作の約束事

- 前提条件に別の指定がない限り、すべての手順を基準状態から始める。
- CSS セレクタや DOM の位置より、ARIA のロールとアクセシブルネームを優先する。
- すべてのコマンドを文字どおりに扱う。引用された名前やフラグを変えない。
- ブラウザの操作は `control-notes browser` で行う。
- 端末の操作は `control-notes cli -- <command>` で行う。
- 変更の後は投入したデータを元に戻す。クリーンアップで証拠を消さない。

## 証明とスキップの報告

- 最終画面だけでなく、ユーザーの操作とその結果の状態を取る。
- UI の証明には、ARIA のスナップショットと、アプリが識別できるスクリーンショットを含める。
- CLI の証明には、コマンド、stdout、stderr、終了コードを含める。
- 変更の証明には、保存された値を読み取り専用の別の画面で見たものを含める。
- どの成果物にも、機能 ID と使った入口を記録する。
- 辿り着けない経路は、試したコマンドと満たせなかった前提条件とともに報告する。
- スキップした入口を、別の経路で検証済みとして報告しない。

## 機能ファイルの約束

各機能ファイルは H1 のタイトルと、ユーザーから見える振る舞いを説明する 1 段落で始まる。続いて、ちょうど 4 つの H2 をこの順で置く。

1. `Sub-features` は短い ID と、振る舞いごとに 1 行を並べる。
2. `How to get to it (user POV)` はユーザーの入口をすべて並べる。
3. `Driving it with <harness>` は `Preconditions:` で始め、ユーザーの操作を正確なコマンドと観察可能な結果に対応させた、ラベル付きの箇条書きにする。
4. `Gotchas` は、検証の実行を無駄にしたり無効にしたりしうる罠を並べる。

実装の詳細は地図に入れない。名指すのは、ユーザーの経路、安定したハンドル、必要な状態、コマンド、観察可能な証明だけ。
