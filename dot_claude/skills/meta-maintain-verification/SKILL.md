# meta-maintain-verification

アプリが変わった瞬間から、機能の地図は腐り始める。このスキルは、`/meta-create-verification` で生成したスキル（または機能の地図を持つ任意のプロジェクト専用の検証スキル）の保守のループだ。厳密さの単位は文ではなく機能だ。すべての機能ファイルをソースから確かめ、すべての機能をライブで動かす。箇条書きを 1 つずつ端末で確かめることまではしない。

## 結果

次のどれかを選び、どれかを明言する:

- **clean**: すべての機能がソースとライブの両方で確かめられ、出すべきものがない。ブランチも PR も作らない。
- **changed**: 証明できた文書・操作手段・地図の修正を 1 つの PR で出す。
- **blocked**: 確認が終わらなかった、または証明できた修正を安全に出せなかった。何が妨げたかを正確に書く。

## 編集の範囲

直すのは地図だけで、プロダクトのコードには触れない。編集してよいのは検証スキル自身のディレクトリ（SKILL.md、features/、スキルが持つ操作用スクリプト）だけ。

地図の古さと退行を区別する。地図が書いている振る舞いをアプリがもうしないとき、それは次のどちらかだ:
- 地図が古い: 地図を直す
- プロダクトの退行: ユーザーに報告する。文書を書き換えてごまかさない

## 手順

0. **対象を見つける。** 保守する検証スキルを探す。本文に起動・操作の節と機能の地図を持つプロジェクト専用スキル（ふつうは `.claude/skills/verify-*/`）。候補が複数あればどれかを聞く。なければ止まり、対象をでっち上げずに `/meta-create-verification` を案内する。

1. **索引の衛生。** 地図の README を読み、同じディレクトリのファイルを glob する。欠け、余分、重複、リンク切れを直す。軽く済ませる。一覧の自動生成はしない。

2. **ソースの確認。** 機能ファイル 1 つにつき 1 体、読み取り専用のサブエージェント（Agent ツールの Explore）を並行に起動する。ソースを読んでまとめるだけの探索なので軽いモデルでよい。各サブエージェントは「このユーザー向けの機能はどう動くか」をソースから説明し、地図の古さの疑いを引用付きで挙げ、ライブで確かめる手順を簡潔に 1 つ返す。サブエージェントはアプリを操作せず、ファイルも編集しない。返す形: 機能の要約 / ソース上の入口 / 地図が古い疑い（なければ「なし」） / 確かめる手順 1 つ。

3. **突き合わせ。** すべての機能ファイルに要約が返ってきていることを確かめる。重なる手順は、なるべく少ないアプリの状態にまとめる。引用された「古い疑い」は抜き取りで確かめる。問題なしとされた主張は証明し直さない。最近の変更を見て、地図にないユーザー向けの表面を探す。ただし「地図にない」と言うには具体的なソースのパスが要る。

4. **ライブの確認。** ソースが問題なさそうでも必須。操作はすべて親が行う。検証スキル自身の起動モデルに従う（サーバーや UI なら長生きするインスタンス 1 つを順番に操作し、短命な CLI なら操作ごとに隔離した新しいセッションを使う。決めるのはこのスキルではなく、検証スキルの Launch 節だ）。すべての機能を少なくとも 1 回動かす。どんな失敗があっても、確認の間ずっと次の 3 つを守る:
   1. 最後に予想外のことをして以来 health check していないインスタンスは操作しない。最初の操作の前に doctor、セッションが単位なら新しいセッションごとに doctor、操作が失敗したら再び doctor。doctor では見えない失敗（プロセスは正常だが UI が固まった状態など）なら、祈らずに既知の状態に戻すか起動し直す。
   2. それまでに取った証拠は、どのクリーンアップの後も残っている。名指しした場所で確かめる。仮定しない。
   3. 操作が始めたものは、その操作の役目が終わった後まで残さない。失敗した反復の残骸は、セッションが固まっていても、終了していても、共有されていても片付ける（共有インスタンスなら、インスタンスではなく残骸を片付ける）。

   スキル側が古いせいで doctor が失敗するなら、それは地図の古さだ。編集範囲の中で直して 1 回だけ再試行する（直したことで無効になったものだけを再起動する）。それでもだめなら `blocked` にする。辿り着けない機能を `verified-unreachable` としてよいのは、具体的な前提条件（認証、権利、OS、外部の状態）と試した経路があるときだけ。地図がその前提条件を書いていないなら、それは地図の古さだ。トリアージで直した操作手段は、出す前にライブで動かし直す。最後の片付けは、そうした再証明も含めた最後の操作の後に行い、実行の後に何も残さない（証拠はスキルの指示どおり残す）。

5. **トリアージ。**
   - ユーザー視点の説明が間違っている・欠けている → 地図の古さ。直す。
   - 振る舞いは正しいのに操作手段が動かせない → 操作手段の穴。直す。生成時と同じくヘルパーの規則に従う（スクリプトは実行可能にし、呼び出し方をスキル本文に書く）。
   - アプリの振る舞いが本当に壊れている → プロダクトの退行。ユーザー向けに記録し、この PR には入れない。

6. **出すか止まるか。** changed なら、証明できた修正を 1 つの PR にまとめる。出す前に変更したファイルをすべて読み直す。clean か blocked なら PR は作らず、結果と確認の範囲を正直に報告する。

実行メモ（確認した機能、辿り着けなかった前提条件、確かめた古さ、結果）は簡潔に一時的な場所に残し、コミットしない。
