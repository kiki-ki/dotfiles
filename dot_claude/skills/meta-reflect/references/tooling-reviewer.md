## 追加の観点: エージェントの自給自足

エージェントが自分で取得できた文脈を、ユーザーが手で渡した瞬間をすべて挙げる（MCP ツール、`gh` などの CLI、別のスキルで取れたもの）。

それぞれ:
- Principle: エージェントが自動で調べるべきだったことを 1 文で。
- Evidence: ユーザーの手渡し（チケット ID、チャットのスレッド URL、トレース ID、エラーのリンク、「これは PR #X から」など）。
- Routing: それが起きたワークフローを持つスキル。次のエージェントが自分で取りに行けるよう、関連するツールや兄弟スキルを呼ぶように拡張する。

例:
- エージェントがチケットを引かなかったので、ユーザーがチケットのタイトルを貼った。Routing: 関連するトリアージのスキルが最初にチケットを引くようにする。
- エージェントが PR を見なかったので、ユーザーが PR の内容を説明した。Routing: 関連するスキルが `gh pr view` を使うようにする。

今のトランスクリプト <ABSOLUTE_PATH> を読む（パスがなければ下の要約を使う）。

探すもの:
- エージェントが発見するはめになったツールの呼び方やコマンドのフラグ
- ライブラリやフレームワークの癖（設定、ロックファイル、環境変数の振る舞い、バージョン固有の落とし穴）
- コードを一目見ても分からないファイルやパスの規約
- テストのコマンド、CI のフラグ、落ちた実行をローカルで再現する方法
- デバッグの入口: トレースの取り方、ログの出る場所、叩くべきエンドポイント
- 初回に数分を奪ったビルド・パッケージマネージャ・サンドボックスの驚き

## セッションで実際に使ったスキルとツールに絞る

指摘は、このトランスクリプトで使われたスキル・ツール・MCP を指すものに限る。親が開いてもいないスキルへの推測の振り分けは数えない。スキルが使われたかは、トランスクリプトで次を探して確かめる:

- `SKILL.md` に対する Read、または Skill ツールの呼び出し
- スキルのパスに言及している Agent へのプロンプト
- スキルに書かれたコマンドと一致するツール呼び出し

有効な指摘の形は 2 つ:

- 親がスキルを使い、その本文に本当の穴を見つけた。スキルの該当節に振り分ける。
- スキルが使えたのに、役立つ場面で呼ばれなかった。次は呼ばれるように description を調整する。`tune description: <skill path>` として振り分ける。

どちらでもないスキルは捨てる。

見つけた長持ちする学びを列挙する。それぞれ:
- Principle: 規約や技術的事実を 1 文で。今後のエージェントが当てはまる場面に気づける程度に具体的に。
- Evidence: トランスクリプト上の正確な箇所（ターン番号か短い引用。コマンドやフラグを含める）。
- Routing: 最も関係する既存スキル（トランスクリプトに現れたとおりの `SKILL.md` のパス）、呼ばれるべきだったのに呼ばれなかったなら `tune description: <skill path>`、それ以外なら `new skill: <kebab-name>`。

些細なこと（typo、再試行）は飛ばす。親が従った既存スキルからすでに明らかなことは飛ばす。移ろう実装の詳細（特定の SHA、今のファイルパス、バージョン番号、正確なバイト数）は飛ばす。規約は一般化できるが、固定された詳細はできない。
