# Build the Lever

作業が自明でないなら、手でやる代わりに、それをやる道具を作る。

**なぜ:** 見返りは 2 つある。スループット: codemod、ジェネレータ、スクリプトは毎回同じやり方で作業し、再実行はタダ。確信: 道具は、レビュアーが読んで再実行し作業を確かめられるひとつの成果物になる。手でやった変更は、やり直す以外に再検証できない。決定的なスクリプトは「信じてくれ」を「これを実行して」に変える。

**パターン:** 既定は道具を作ること。飛ばすのは、一目で分かる明らかな編集が 2、3 個というような自明な作業のときだけ。

- 最初の 1 単位は手でやって手順を学び、それから道具を作る。その単位で道具を再実行し、手でやった版と diff して証明する。道具は再実行しても安全にする。
- 編集には codemod かスクリプト、繰り返しのファイルにはジェネレータ、分析には sqlite に吐き出してのクエリ、検証には再実行できるチェック。
- 決定的な道具はファンアウトに勝る。道具が全単位を一度に処理できるなら自分で実行する。スクリプトでできることを手で適用させるためにサブエージェントを並べない。
- サブエージェントに作業を配るときは、道具を全員が読むスキルとして書く: 手順、検証の約束、触ってはいけない範囲をひとつの成果物にまとめる。サブエージェントが約束をこっそり書き換えられないよう、その書き込み範囲の外に置く。
- この原則を適用すると、ファイルがひとつ生まれる。この原則を挙げたのに diff に codemod・スクリプト・ジェネレータ・委任用スキルがないなら、適用していない。
- 作業がセッションより長く生きるなら、道具をコミットする。

**バランス:** 基準は繰り返しではなく自明さだ。一度きりの作業でも、道具があることで作業を確かめられるようになるなら道具を作る価値がある。[principle-laziness-protocol](../principle-laziness-protocol/SKILL.md) に従い、仕事をする・証明する最小のスクリプトを作る。フレームワークは作らない。
