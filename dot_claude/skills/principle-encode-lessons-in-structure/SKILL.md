# Encode Lessons in Structure

繰り返し起きる修正は、文章の指示ではなく仕組み（ツール、コード、メタデータ、自動化）に埋め込む。すべてのエラー、人間からの訂正、予想外の結果は学習のシグナルだ。捉え、行き先を決め、ループを閉じる。

**なぜ:** 文章の指示は見落とされやすい。読み手が気づき、覚え、従う必要がある。構造的な仕組み（lint ルール、メタデータのフラグ、実行時チェック、自動化スクリプト）は協力なしにルールを強制する。

**パターン:**
同じ指示を二度書こうとしていると気づいたら:
1. 問う: これは lint ルール、メタデータのフラグ、実行時チェック、スクリプトにできるか。Claude Code なら hook（settings.json の hooks）や権限設定（permissions の allow / deny）にできるか
2. できるなら埋め込む。指示は消す
3. できない（判断が要る）なら、指示をより目立たせ、失敗例を添える

**最も強い仕組みを選ぶ。** 複数の仕組みが使えるなら、状況が許す最も強いものを選ぶ（コンパイルできない表現不能な状態 → CI を落とす lint や禁止 API → 正規のヘルパー → 実行時チェックの順）。エージェントは周囲のコードがやっていることを真似るので、弱いガードは次のテンプレートになる。

**系:** 修正が構造的なら、構造的な修正だけを使う。指示は症状だ。

**フィードバックループ:**
- **訂正をすべて捉える。** 人間が介入したりテストが落ちたりしたら、一度きりかパターンかを判断する。
- **正しい層に送る。** 一度きり → 記録しない。繰り返す修正 → lint、hook、権限設定、スキル。プロジェクトの約束事 → そのプロジェクトの CLAUDE.md。システム的な問題 → 原則。memory は揮発するので、残すべき学びの置き場にしない。
- **ループを閉じる。** 記録するだけで終わらせない。今適用するか、具体的な todo を作る。

**アンチパターン:**
- 記録せずに了解だけする（「覚えておきます」は残らない）
- 行き先を決めずに記録する（あるべき lint ルールについてのメモは、そのルールが実装されなければ無駄）
- 一般化せずに直す（一箇所だけ直して、繰り返すパターンを残す）
