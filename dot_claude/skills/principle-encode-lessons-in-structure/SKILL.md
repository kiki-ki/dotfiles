# principle-encode-lessons-in-structure

繰り返し起きる修正は、文章の指示ではなく仕組みで守らせる。文章の指示は、読み手が気づき、覚え、従わない限り効かない。lint、実行時チェック、スクリプトは、読み手が協力しなくてもルールを守らせる。

## 同じ指示を二度書こうとしたら

1. lint、メタデータ、実行時チェック、スクリプトにできないかを考える。Claude Code なら hook（settings.json の hooks）や権限設定（permissions の allow / deny）も候補になる。
2. できるなら仕組みにして、文章の指示は消す。
3. できない（判断が要る）なら、指示を目立つ場所に移し、失敗例を添える。

複数の仕組みが使えるなら、いちばん強いものを選ぶ。強い順に、コンパイルできない型、CI を落とす lint や禁止 API、正規のヘルパー、実行時チェック。エージェントは周りのコードを真似るので、弱いガードは次のコードの手本になってしまう。

仕組みで直せるなら、仕組みだけで直す。文章の指示を足すのは症状への対処だ。

## 訂正を受けたら

- 人間に訂正されたりテストが落ちたりしたら、一度きりか、繰り返すパターンかを判断する。
- 置き場を決める。一度きりなら記録しない。繰り返す修正は lint・hook・権限設定・スキルへ。そのプロジェクトだけの約束事はそのプロジェクトの CLAUDE.md へ。どこでも起きる問題は原則へ。memory は揮発するので置き場にしない。
- その場で適用するか、具体的な todo にする。「覚えておきます」は何も残らない。あるべき lint ルールのメモも、ルールを実装しなければ意味がない。1 箇所だけ直して、同じパターンを残さない。
