# principle-laziness-protocol

最小のコードと複雑さで目的を果たす。複雑なシステムに足すと複雑さは膨らむ一方なので、先に消してから作る。消せばコードが減り、本当に必要な構造が見え、次の設計が決まりやすくなる。

## 足す前に消す

- デッドコード、冗長なバリデータ、中身のない参照を消してから、単純になった土台の上に作る。
- 磨く前に削る。最小の形にしてから品質に手をかける。
- 想像上のエッジケースではなく、実際の使われ方に合わせて設計する。仕様が求める以上のバリデータ・パーサー・ガードを書かない。
- 新しい内容のない参照やプロンプトの指示は、スタブとして残さず消す。
- 触る前より少し単純な状態にして終える。

## 最小の変更にする

- 問題を解く最小の変更をする。見栄えのよい定型コードより行数の少なさを取る。
- 同じ判断を複数の場所に書かない。1 箇所で判断し、結果を単純なフラグとして渡す。
- 新しい値を型・スキーマ・パイプラインなどのレイヤーに通す必要が出てきたら、手を止めて、もっと直接の経路を探す。
- 分岐や boolean が増え続けるなら、状態を 1 つの型（状態機械や判別共用体）で表す。
- 「この値はどこから来て、何が書き換えうるか」に 30 秒で答えられない構造なら、レイヤーか状態を減らす。
- 書く前に、次の順に探して最初に当てはまったもので止まる。そもそも必要か、このコードベースにもうあるか、標準ライブラリで足りるか、プラットフォームの機能で足りるか、導入済みの依存で足りるか。どれでもなければ、動く最小のコードを書く。

## 手を抜かないところ

- 問題の理解。短くするのは解決策であって、読むことではない。変更が触れるファイルと実際の処理の流れを追ってから選ぶ。
- 信頼境界での入力検証、データの損失を防ぐエラー処理、セキュリティ。

人間の開発者が保守にうんざりするコードなら、それは悪い解決策だ。
