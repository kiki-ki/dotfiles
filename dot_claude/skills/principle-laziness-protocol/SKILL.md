# Laziness Protocol

最小のコードと複雑さで、最大の成果を出す。システムを発展させるときは、先に複雑さを取り除き、それから作る。

**なぜ:** 複雑なシステムに足すと、複雑さが複利で増える。先に消せばコードが減り、本質的な構造が見え、次の設計が自明になることが多い。

## 足す前に消す

- 構築の前に削除を置く。デッドコード、冗長なバリデータ、中身のない参照を消してから、単純になった土台の上に作る。
- 磨く前に削る。品質に投資する前に最小まで持っていく。
- 推測上のエッジケースではなく、観測された使われ方に合わせて設計する。仕様が求める以上の推測的なバリデータ・パーサー・ガードを書かない。
- 新しい内容のない参照やプロンプトの指示は、スタブとして残さず消す。
- 見つけたときより、同じかより小さな表面の裏で、少し単純な設計にして去る。

## 最小の変更

- **diff を最小にする。** 問題を解く最小の変更をする。「エレガントな」ボイラープレートより行数の少なさを取る。
- **判断を一箇所に集める。** 同じ選択を複数の場所で繰り返さない。一つの信頼できる情報源の裏に置き、結果を単純なフラグとして渡す。
- **引き回しを疑う。** 新しいシグナルを型・スキーマ・パイプラインなどのレイヤーに通す作業になったら、立ち止まってもっと直接的な経路を探す。
- **書く前に、上から順に探して最初に成り立つもので止まる:** そもそも必要か → このコードベースに既にあるか → 標準ライブラリで足りるか → プラットフォームの機能で足りるか → 導入済みの依存で足りるか → それでもなければ動く最小のコード。

## 怠けてはいけないところ

- 問題の理解。短くしてよいのは解決策であって、読むことではない。変更が触れるファイルと実際の流れを追ってから選ぶ。
- 信頼境界での入力検証、データ損失を防ぐエラー処理、セキュリティ。

**判定基準:** 人間の開発者が保守するのにうんざりするコードなら、それは悪い解決策だ。
