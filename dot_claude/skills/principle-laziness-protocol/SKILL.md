# Laziness Protocol

最小のコードと複雑さで、最大の成果を出す。

- **削除を優先する。** リファクタや改善を頼まれたら、足す前に消せるものを探す。
- **呼び出し階層を平らに保つ。** 深い呼び出しの連鎖を避ける。大きな仕事を隠す豊かなインターフェースは深い連鎖ではない。ある問いに答えるのに 3 つ以上のファイルやレイヤーを辿る必要があるなら、平らにする。
- **判断を一箇所に集める。** 同じ選択を複数の場所で繰り返さない。一つの信頼できる情報源の裏に置き、結果を単純なフラグとして渡す。
- **diff を最小にする。** 問題を解く最小の変更をする。「エレガントな」ボイラープレートより行数の少なさを取る。
- **引き回しを疑う。** 新しいシグナルを型・スキーマ・パイプラインなどのレイヤーに通す作業になったら、立ち止まってもっと直接的な経路を探す。
- **小さな漏れを放置しない。** 小さな素通しのラッパー、表現の漏れ、重複した選択は、広がる前に消す。小さな漏れは積み重なって恒久的な調整コストになる。

**判定基準:** 人間の開発者が保守するのにうんざりするコードなら、それは悪い解決策だ。
