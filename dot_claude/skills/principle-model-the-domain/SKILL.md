# Model the Domain

現実のドメインを、条件分岐に散らばらせず、データ構造に埋め込む。

**なぜ:** 散らばった boolean、繰り返される形の前提、ファイルをまたいで広がる分岐は、偶有的な複雑さだ。ドメインに合った構造は不正な状態を表現不能にし、分岐を消す。書く時点で選べば安い。後から取り戻そうとするとリファクタに見えて先送りされる。

**たとえばこういう構造に手を伸ばす:**

- 散らばった boolean・フェーズ・ライフサイクルのチェックの代わりに、状態機械
- ばらばらの引数や繰り返される形の前提の代わりに、型付きのオブジェクト／モデル
- ファイルをまたいで広がる分岐の代わりに、map、レジストリ、ルックアップテーブル、判別共用体
- その場しのぎの状態変更の代わりに、reducer やコマンド／イベントモデル
- 読み込み・検証・変換・保存のような手順の列ではなく、ひとつのドメイン知識のまとまりを中心に組織したモジュール。実行順は所有権ではない
- 繰り返される振る舞い・所有権・不変条件を集める小さなモジュール境界
- データのアクセスパターンが求めるなら、キュー、キャッシュ、インデックス、グラフ／木、正規化されたコレクション
- ほかに合う構造なら何でも。どれも合わないときは、コードが決して許してはいけないことと、データがどう読まれるかを突き止め、それをちょうど表す構造を探す

抽象化を無理強いしない。今の形が明確で、局所的で、育ちそうにないなら退屈なコードを選ぶ。分岐・重複したルール・不正な状態・ライフサイクルのリスクを消さずに間接参照だけ増やす抽象化は疑う。

この原則を飛ばした兆候: 新機能が既存の if/else の連鎖を 1 つ伸ばす。1 つ目と同期し続けなければならない 2 つ目の boolean が現れる。時間軸での分解もそうだ。フェーズの名前がついたモジュールは、同じドメインルールを各ステップで繰り返す。
