# Sequence Verifiable Units

作業を、それぞれ確かめられる状態で終わる小さな単位の列として並べ、今の単位が green になるまで先へ進まない。

**なぜ:** 原因となった単位で見つかった破損は、局所化が安い。まとめて処理した後に見つかった破損は埋もれていて、しかも壊れた土台の上にもう積み上げてしまっている。同じ単位を、レビュアーが再生できる届け方に並べれば、「信じてくれ」が「red になって、green になるのを見てくれ」に変わる。

**実行。** 一斉置換や移行など、似た編集の連続では、次に進む前に各変更を検証する。各単位は前後の括弧になる: 既知の正常状態、変更ひとつ、チェックの実行、それから次へ。最初にきれいなトランクへ rebase し、すべてのチェックが本当の基準線に対して測るようにする。道具（lever）が編集をするなら単位ごとのチェックはほぼタダだ。それでも実行する。

**届け方。** コミットと PR は、作業を証明する順に積む。典型は、先に失敗するテスト、その上に修正。ほかにも、形を変える前の引き算、処置の前の基準値の取得、機能の前の足場、といった順序がある。各コミットは単独で成立し、列全体が論証として読める。

各チェックを本物に保つ principle-prove-it-works と、単位ごとのチェックを安くする principle-build-the-lever を補う、順序づけの原則。
