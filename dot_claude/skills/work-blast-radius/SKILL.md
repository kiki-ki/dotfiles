# work-blast-radius

変更が出荷される前に、それがどこか別の場所で何を壊すかを探す。

呼び出し元の一覧を作るのは仕事ではない。それは grep で一瞬で出る。仕事は、grep では見えない破損を見つけることだ。

## 自分の書いた説明を信じない

もっともらしく聞こえる影響範囲の説明には価値がない。正しくても間違っていても、同じくらい説得力があるからだ。だから説明を返して終わりにしない。全体が依存している 1〜2 個の事実を見つけ、コードを動かして証明する。

### どれだけ確かか

変更の安全性が依存する事実ごとに、安く済む範囲で次の段階をできるだけ下まで進め、どこで止まったかを書く。

1. そう言った。それだけでは無価値。
2. その行を示した。実在する `file:line` か、ライブラリ自身のソース。
3. 悪いケースが起こりえないことを示した。失敗を一歩ずつ辿り、そこに届かないことを確かめた。
4. 動かした。本物のコードを呼び、間違っていれば大きな音を立てて落ちるスクリプトかテスト。
5. 動いているアプリで再現した。

段階 4 はたいてい、アプリが同梱しているのと同じライブラリを import し、気になっている関数そのものを呼ぶ小さなスクリプト 1 つで済む。

## 手順

1. **変更を読む。** diff、追加・変更・削除されたシンボル、そして diff が明示していない部分も含めて、今何が違う動きをするか。PR とコミットは `gh pr view`、`git log`、`git show` で引く。
2. **安全の根拠になる事実を 1 つ見つける。** 危なく見える変更の多くは、「この呼び出しはすでに死んだキャッシュのエントリを捨てるだけで、他に何もしない」のような 1 つの事実のおかげで安全だ。その事実を見つける。それが成り立てば、危ないケースの大半が一度に片付く。可能性を長々と並べるより、ここに時間を使う。
3. **grep が止まる先を見る。** 呼び出しているライブラリのソースを読み、固定されたバージョンとローカルのパッチを確かめる。いつ実行されるかを突き止める: マイクロタスク、アンマウントや破棄、フレームワーク固有のライフサイクル。シンボル検索が見落とすものを追う: API が返す JSON、DB のカラム、ワイヤーフォーマット、同じバイト列を読む別言語のコード、feature flag、3 ホップ先のコード。
4. **各リスクに正直になる。** 起きる現実的な確率と、起きたときの現実的なコストを付ける。確かめたリスクを残し、確かめて問題なしとしたものは別に並べる。実在する `file:line` を引用する。何も見つからない検索もひとつの答えだ。呼び出し元や API をでっち上げない。
5. **その 1 つの事実を証明する。** 本物のコードを動かすスクリプトかテストを書き、実行し、結果を貼る。

## 返すもの

- **何をするか。** 何が変わったか。自明でない部分も含めて。
- **安全の根拠になる 1 つの事実。** それを述べ、どの段階まで進めたかを書き、証明を示す。証明できなかったら「未証明」と書く。
- **リスク。** それぞれ、どう壊れるか、`file:line`、どれくらい起きやすく、どれくらいひどいか、どう確かめるか。重要なものには証明を貼る。
- **問題なしとしたもの。** 何を確かめ、なぜ大丈夫か。
- **マージの前に。** 本当のバグを捕まえる最も安いテストか再現手順。書いたスクリプトも含める。

公開の場に出す前に、実在するコードを引用し、非公開の情報を取り除く。

**返答:** 上の説明と、安全の根拠になる事実が「証明済み」か「未証明」か。
