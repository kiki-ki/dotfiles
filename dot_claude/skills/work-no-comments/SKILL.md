# work-no-comments

コメントの判定をサブエージェントに任せ、その結果を検査し、受け入れたものに対処する。

判定を別のエージェントに任せるのは、「このコメントの情報はコードから読めるか」は、書いた本人には判断できないからだ。書いた本人は文脈を知っているので、どのコメントも必要に見える。

## 範囲

呼び出し元が渡したファイルか diff。なければ、ベースブランチ（既定は `main`）に対する今の diff（作業ツリーを含む）。

## 残すコメントと消すコメント

判定の規則は [references/checker-prompt.md](references/checker-prompt.md) にある。要点:

- 残す: コードから読めない「なぜそうしたか」、壊してはいけない不変条件、回避策の理由、外部の依存・プラットフォーム・プロトコルに強いられた挙動、ライセンスヘッダ、公開 API の契約を定める doc コメント、コードで表せない制約を説明する issue や RFC へのリンク
- 消す: コードをなぞるだけの説明、見出し代わりのコメント、コメントアウトされたコード、今のコードと食い違う古いコメント

## 手順

1. **判定を任せる。** Agent ツールで general-purpose を 1 体起動する。[references/checker-prompt.md](references/checker-prompt.md) の全文と範囲を渡す。規則を言い換えたり要約したりしない。判定役が触ってよいのはコメントだけで、判定役は削除と、`RESHAPE` / `SUPPRESSION` のフラグを返す。
2. **結果を検査する。** 判定役の報告と diff を読み、次を却下する:
   - コメント以外への編集
   - 範囲外への編集
   - 「残すコメント」に当たるものの削除
   - 理由が事実と違うフラグ
   - 意図して残しているコードを悪者扱いするフラグ

   却下した削除は元に戻す。判定があいまいで判断できない削除は、戻さずそのままにする。スコープ内の lint や型チェックの抑制で、判定役が見落としたものがないかも確かめる。報告に問題があって却下したら、問題点を名指しして 1 回だけやり直させる。2 回目も却下なら、未解決として報告して終える。
3. **小さな修正をする。** 受け入れた `RESHAPE` のうち、名前の変更、定数への切り出し、型の追加、デッドパスの削除、本物の API を使う、といった小さなもので済むものは直接直す。コードで表せるようになったコメントは消す。形を変える必要がある修正は、スケッチを示してそこで止め、ユーザーの判断を待つ。
4. **回避策は根本から直す。** 受け入れた回避策のフラグは、[principle-fix-root-causes](../principle-fix-root-causes/SKILL.md) に従い、範囲内で最小の根本修正をする。根本原因が範囲外なら、範囲内の最小の修正にとどめ、残りを未解決として報告する。症状を黙らせるガードを足さない。
5. **制約を仕組みにできないか提案する。** 「消すな」「文言を変えるな」「変える前に X に相談」といった制約のコメントが、自分たちで変えられないことについてなら残す。自分たちのコードについてなら、[principle-encode-lessons-in-structure](../principle-encode-lessons-in-structure/SKILL.md) に従い、範囲内で最も安い担保（型、実行時チェック、テスト、lint）を提案し、承認を待つ。承認されたら担保を入れてからコメントを消す。承認されなければコメントは残し、制約を未担保として報告する。
6. **報告する。** 削除数、戻したコメント、やり直しの回数、スケッチ、行った修正、担保の提案と実施したもの、担保されていない制約、その他の未解決事項。
