# 文書の種類ごとの要素と失敗

該当する節だけを読む。当てはまる節がなければ、いちばん近い節を使う。issue は work-create-github-issue スキルに従う。

「欠かせないもの」は、抜けていないかを確かめるための一覧で、節の見出しの型ではない。材料にないものは節を作って埋めず、欠けていて困るならユーザーに聞く。

## PR 本文

欠かせないもの:

- なぜ変えるか。diff からは分からない動機や、起きていた問題
- どう確かめたか。実行したコマンドと、その結果
- レビュアーに判断してほしい点があれば、その点

出やすい失敗:

- ファイルや関数ごとの変更を列挙する。diff を見れば分かる
- 確かめていない「影響なし」「テスト済み」や、材料にない挙動の説明を書く
- セッションの経緯（試した順番、ユーザーとのやり取り）をそのまま書く。捨てた案は、レビュアーが同じ案を思いつきそうなときだけ、捨てた理由と一緒に 1 文で書く
- 数行で済む本文に「概要」「変更内容」「テスト」の見出しを付ける

## README

欠かせないもの: 何のためのものか（最初の 1〜2 文）、使い始めるまでの最短の手順、よく使う操作。

出やすい失敗: 宣伝文句や特長の列挙から始める。すべてのオプションを並べる（リファレンスに分ける）。変更履歴を書く。

## 設計メモ・ADR

欠かせないもの:

- 決めたこと。冒頭に 1〜2 文で書く
- そう決めた理由になった制約と事実
- 検討して捨てた案と、捨てた理由
- この決定で失うもの、または見直す条件

出やすい失敗: 背景から書き始めて、決めたことが後半に埋もれる。利点だけを書き、失うものを書かない。誰も選ばない案を並べて、捨てた案に見せかける。

## 手順書

欠かせないもの: 前提条件（手順の前にまとめる）、番号付きの操作、各操作の後に何が見えるはずか、失敗したときの見分け方。

書き方:

- 1 つのステップには 1 つの操作だけを書く
- 目的や条件を操作の前に書く。「設定を消すには、`foo reset` を実行する」
- 必須でないステップは、先頭に「任意:」と書く

出やすい失敗: 背景の説明を手順の間に挟む（リンクにする）。「簡単に」「単に」と書く。操作の結果を書かない。「上の」「下の」のように位置で指す。

## リファレンス

説明する対象（コマンド、設定、API）と同じ構造で、既定値・取りうる値・制約・エラーを書く。

出やすい失敗: 意見や勧めを混ぜる。手順を混ぜる。コードから生成できるものを手で書き、古くする。

## 解説

なぜそうなっているか（設計判断、経緯、制約、別案）を書く。意見を書いてよいのはこの種類だけ。

出やすい失敗: 手順やリファレンスの表を混ぜる。長所と短所を並べるだけで、書き手の判断を書かない。

## チュートリアル

手を動かしながら学ぶ文書。最初に何を作るかを書き、各ステップで何が見えるはずかを書く。説明は 1 文とリンクにとどめる。
