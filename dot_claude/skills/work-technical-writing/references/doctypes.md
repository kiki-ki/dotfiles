# 文書の種類ごとの要素と失敗

「欠かせない」は抜けを確かめる一覧で、見出しの型ではない。材料にないものは節を作って埋めず、困るならユーザーに聞く。issue は work-create-github-issue スキルに従う。

- PR 本文。欠かせない: なぜ変えるか、どう確かめたか（コマンドと結果）、判断してほしい点。失敗: 材料にない挙動を書く。捨てた案を、レビュアーが思いつきそうにないのに書く。数行の本文に見出しを付ける。
- README。欠かせない: 何のためのものか（最初の 1〜2 文）、使い始める最短の手順、よく使う操作。失敗: 宣伝文句から始める。全オプションや変更履歴を並べる。
- 設計メモ・ADR。欠かせない: 冒頭に決めたこと、理由になった制約と事実、捨てた案と理由、失うものや見直す条件。失敗: 決めたことが後半に埋もれる。失うものを書かない。誰も選ばない案を捨てた案として並べる。
- 手順書。欠かせない: 手順の前の前提条件、番号付きの操作、各操作の後に見えるもの。書き方: 1 ステップ 1 操作。目的や条件を操作の前に書く（「設定を消すには、`foo reset` を実行する」）。失敗: 手順の間に背景を挟む。「簡単に」と書く。「上の」「下の」で指す。
- リファレンス。対象と同じ構造で、既定値・取りうる値・制約・エラーを淡々と書く。意見や手順を混ぜない。
- 解説。なぜそうなっているか（設計判断、経緯、制約、別案）を書く。意見を書いてよいのはここだけで、長所と短所を並べるだけでなく判断まで書く。
- チュートリアル。最初に何を作るかを書き、各ステップで何が見えるはずかを書く。説明は 1 文とリンクにとどめる。
